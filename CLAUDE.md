# Math 195 capstone: predicting mutual interest before two strangers meet

Read this file first in every session. PROJECT.md has the full plan, team, timeline and references.
PREREG.md has the hypotheses; it is committed before the analyses that test them run.

## What this project is

A three-person course project (Sophia Qin, PM; Jenna Yang, mathematical lead; Abraham Yeung, technical) on
the Columbia speed-dating experiment. Main question: how well can a mutual match be predicted from
information available before the date, and which pair characteristics matter? Secondary: how much does the
four-minute meeting add, measured by comparing a pre-meeting model set with a set that also uses the
in-date ratings. Second half: the rows are correlated through shared people and events, so the usual
cross-validation error bars are too narrow; we measure by how much and which constructions are honest.
One further question is chosen in week 4 (desirability ranking, or the accuracy of participants' own
predictions).

The team decided to finish the plain predictive analysis before adding anything complex. Respect that order.
The additions are not vague: PROJECT.md lists them in four tiers with status, and some are already partly
done (the error-bar simulation, the real-data error-bar run, and four proved propositions in proposals/06).

## Conventions

1. Pre-registration. Hypotheses live in `PREREG.md` and are committed before their tests run. Never edit a
   hypothesis after its test; add a new numbered one with the date and reason in the change log.
2. Two feature sets, named everywhere: `pre` (known before the date) and `pre+date` (adds the in-date
   ratings). Every result table says which set it used.
3. Unit of analysis. Match prediction uses one row per dyad, with the two people's features ordered by gender
   (`f_` and `m_` prefixes) plus pair features (`age_diff`, `int_corr`, `same_field`, `same_goal`, preference
   alignment in both directions). Yes prediction uses one row per date from one side.
4. Fold schemes are explicit. Every CV result names its scheme: `random-row` or `event` (whole waves held
   out). Headline numbers use `event`. `random-row` appears only in the leakage comparison.
5. Metrics: error rate, balanced accuracy, sensitivity, specificity, AUC. Matches are 16.5% of dyads, so
   never report error rate alone; choose thresholds on training folds only.
6. Error bars on cross-validated metrics use the cluster-robust estimator (unbalanced form: sum over
   clusters of squared within-cluster residual sums, times G/(G-1), over n squared) at minimum. Never report
   the naive standard error alone.
7. Check every intermediate result. Any function that computes a variance, a fold assignment, or a pair-level
   feature gets a test against a case with a known answer before its output is used.
8. Demographics. Age, field, career, goals, interests are predictors. Race and race-preference variables
   (`race`, `samerace`, `imprace`) are used only if the team records that decision in PREREG.md, are reported
   with the original authors' framing, and are never a target.
9. Environment: Python 3, packages pinned in `requirements.txt`. Seed every random operation and record the
   seed in the output. Outputs go to `results/` as CSV tables and PNG figures named after the script that
   made them. Nothing is pasted into a report by hand.
10. Reports. Each week produces a WR section and a PRPR; scripts should print the numbers those need.

## First session, in order

1. Create the environment, run `scripts/clean.py`, and confirm `data/clean_summary.md` shows 8,368 rows,
   7,031 complete cases, zero rows failing the wave and match checks. Run the other two scripts and confirm
   their numbers match proposals/06 sections 7 and 7b. Report any discrepancy before doing anything else.
2. Write `scripts/pairs.py`: build the one-row-per-dyad table from `data/clean.csv` with `f_`/`m_` features,
   the pair features in convention 3, the `match` response, and the two feature-set column lists saved as
   JSON. Test: 4,184 rows; `match` rate 0.165; every pair feature symmetric where it should be.
3. Write `scripts/eda.py`: yes-rate and match rate by gender and event, distributions of the six ratings,
   dates per person, missingness table, interest-similarity and age-difference distributions by match status.
   Figures to `results/`.
4. Write `scripts/part1_models.py`: logistic regression, LDA, QDA on `match` with the `pre` set under
   `event` 5-fold CV and cluster-robust error bars; then the same with `pre+date`; a coefficient table for
   the logistic models; the stated-versus-revealed table from the yes model.
5. Only then: the lasso, the tree models, and the error-bar study, following the week-by-week plan in
   PROJECT.md.

## Things not to do

- Do not start the error-bar study or the further question before the Part 1 model table exists.
- Do not use random-row CV for any headline number.
- Do not report a variance estimate that has not been checked on the simulation.
- Do not change a pre-registered hypothesis after its test has run.
- Do not load any dataset about real Stanford students (Date Drop, Marriage Pact, Senior Scramble, apps)
  without written permission from the data owner and the instructor's confirmation on IRB requirements.
